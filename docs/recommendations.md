# Recommendations

## Overview

The recommendations engine surfaces up to 5 problems per day that a user should solve next. The selection logic is: find the concepts the user is weakest in but has all prerequisites for, then find unsolved problems tagged with those concepts ordered by difficulty.

Recommendation text is generated by Claude haiku, then cached in Redis for 24 hours. The cache is invalidated on sync and on confidence updates.

## GetRecommendations gRPC

NestJS calls the Go processor's `GetRecommendations` RPC when the Redis cache is cold:

```protobuf
rpc GetRecommendations(GetRecommendationsRequest) returns (GetRecommendationsResponse);

message GetRecommendationsRequest {
  string user_id = 1;
}

message GetRecommendationsResponse {
  repeated Recommendation recommendations = 1;
}

message Recommendation {
  string concept_id = 1;
  string concept_name = 2;
  float  current_strength = 3;
  Problem problem = 4;
  string ai_reason = 5;
}
```

## Algorithm

### Step 1 — Find unlocked weak concepts (Neo4j)

Query: concepts where:
- The user's `HAS_SKILL.strength` is below 60, OR the user has no `HAS_SKILL` edge to the concept (strength = 0)
- AND every concept that has a `REQUIRES` edge pointing to this concept has `HAS_SKILL.strength >= 60` for this user (prerequisites met)
- OR the concept has no prerequisites at all

Results are ordered by ascending strength and limited to 5.

This is the **UnlockedWeakConcepts** query. A concept with no prerequisites is always unlocked — it can appear in recommendations even for new users.

### Step 2 — Find an unsolved practice problem (PostgreSQL)

For each unlocked weak concept, one problem is selected from PostgreSQL:

```sql
SELECT * FROM problems
WHERE concept_ids && ARRAY[$1]          -- concept appears in problem's concept list
  AND external_id NOT IN (              -- user hasn't solved it
    SELECT problem_id FROM codeforces_submissions
    WHERE user_id = $2 AND verdict = 'OK'
  )
ORDER BY
  CASE difficulty
    WHEN 'easy'   THEN 1
    WHEN 'medium' THEN 2
    WHEN 'hard'   THEN 3
    WHEN 'expert' THEN 4
  END ASC
LIMIT 1
```

Difficulty ordering (easy → medium → hard → expert) ensures users get appropriately levelled problems.

**Bug fixed:** The original query used `SELECT DISTINCT` with an `ORDER BY CASE` expression that was not in the select list, which PostgreSQL rejects with: `"for SELECT DISTINCT, ORDER BY expressions must appear in select list"`. Fixed by wrapping in a subquery.

**Bug fixed:** Initial Go code referenced wrong column names (`problemId`, `problemName`, `tags`, `rating`). Actual PostgreSQL columns are `external_id`, `title`, `concept_ids`, `difficulty`, `link`. Fixed by correcting all column references.

### Step 3 — Generate AI reasoning (Anthropic Claude)

For each recommendation, the Go processor calls the Anthropic Claude API:

- Model: `claude-haiku-4-5-20251001`
- Timeout: 15 seconds
- Prompt: includes the concept name, current strength percentage, and problem title

On success the response is a 1–2 sentence explanation of why practising this concept now will help the user progress.

On failure (timeout, API error, rate limit) the system falls back to a template string:

```
Practise {problem_title} to strengthen your {strength}% skill in {concept_name}
```

This fallback ensures recommendations are always returned even when the AI provider is unavailable.

## Redis Caching

### Cache key

```
recommendations:{userId}
```

### TTL

86400 seconds (24 hours). Recommendations regenerate once per day by default.

### Invalidation

The cache is explicitly deleted (not expired) in two cases:

| Event | Invalidation |
|---|---|
| `POST /codeforces/sync` completes | Redis `DEL recommendations:{userId}` |
| `POST /recommendations/confidence` completes | Redis `DEL recommendations:{userId}` |

This ensures that after a sync or after rating a problem, the next dashboard load generates fresh recommendations based on the updated skill profile.

### Resilience

`RedisService` is a `@Global()` NestJS module using `ioredis` with `lazyConnect: true` and `maxRetriesPerRequest: 1`. All `get`, `set`, and `del` operations are wrapped in try/catch — on any error they silently return `null`. The application works correctly with no Redis available; it just regenerates recommendations on every request.

## Confidence Rating

After solving a recommended problem, users rate their confidence 1–5:

```
POST /recommendations/confidence
{ "conceptId": "binary-search", "confidence": 4 }
```

The confidence value is mapped to a strength delta and passed to the Go processor via `UpdateConfidence` gRPC:

| Rating | Meaning | Effect |
|---|---|---|
| 1 | Very unsure | Small positive delta |
| 2 | Somewhat unsure | Moderate positive delta |
| 3 | Neutral | Moderate positive delta |
| 4 | Fairly confident | Larger positive delta |
| 5 | Very confident | Largest positive delta |

The Go processor updates `HAS_SKILL.strength` in Neo4j and the Redis cache is invalidated so the next dashboard load recalculates recommendations.

## Response Format

NestJS returns recommendations to the frontend as:

```json
[
  {
    "conceptId": "binary-search",
    "conceptName": "Binary Search",
    "currentStrength": 34.5,
    "problem": {
      "externalId": "702C",
      "title": "Cellular Network",
      "difficulty": "medium",
      "link": "https://codeforces.com/problemset/problem/702/C"
    },
    "aiReason": "Binary search on answer is a pattern that appears in 30% of Div 2 C problems. Strengthening this from 34% will unlock Dijkstra and BFS variants."
  }
]
```

## Frontend rendering

The `DailyRecommendations` component renders each recommendation as a card:

- Concept badge (colored by strength tier)
- Problem title as a link to Codeforces
- Difficulty badge (`easy` / `medium` / `hard` / `expert`)
- AI reason in italic
- Confidence rating buttons (1–5), which call `POST /api/confidence` and trigger `router.refresh()`
